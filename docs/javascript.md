# JavaScript and Vue integration

The npm packages are unreleased workspaces: `packages/satchel` (`@dgtlss/satchel`) and `packages/vite-plugin-satchel` (`vite-plugin-satchel`). They build ESM and declarations with tsup, use TypeScript, and are tested with Vitest. The Composer package stays at the repository root, with its API and source unchanged.

## Plugin API

```ts
import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';
import satchel from 'vite-plugin-satchel';

export default defineConfig({
  plugins: [vue(), satchel({
    manifest: 'bootstrap/cache/satchel.json', // default; absolute or relative to Vite root
    eager: false,                           // default; true uses eager modules
    dts: 'resources/js/satchel-pages.d.ts',  // default; false disables output
  })],
});
```

Generate the manifest on the build machine with `php artisan satchel:manifest` before starting Vite (Composer package discovery also does this). Version 1 is required. Unsupported versions, missing files, and invalid schema produce an Artisan regeneration hint.

The plugin preserves existing `server.fs.allow` paths and adds registered canonical package paths. Composer path-repository roots can be symlinks outside the app root. Directory symlinks *beneath* a registered root are excluded, matching PHP inventory. File symlinks escaping a declared root fail the build. Only registered namespaces, valid page names, and their configured extensions are imported.

## Generated code

The Vue example's `virtual:satchel/pages` contains the following literal code. Paths are relative to the synthetic module's directory at the Vite root, so it also works when the package lives outside the app:

```js
const overrides = import.meta.glob([
  './resources/js/Pages/vendor/acme-billing/**/*.vue',
], { eager: false, exhaustive: true });

const namespace0 = import.meta.glob([
  '../../tests/Fixtures/AcmeBilling/resources/js/Pages/**/*.vue',
], { eager: false, exhaustive: true });

export default {
  overridePath: './resources/js/Pages/vendor',
  overrides,
  namespaces: [{
    namespace: 'acme-billing',
    path: '../../tests/Fixtures/AcmeBilling/resources/js/Pages',
    extensions: ['vue'],
    pages: namespace0,
  }],
};
```

Each configured extension becomes a literal glob, in manifest order. Exclusions are added for unsafe/unsupported page paths. Vite transforms the calls into imports, retaining normal code splitting and Vue compilation. `eager: true` changes both calls to eager imports. The module is provided through Vite's public `resolveId`/`load` hooks at a synthetic absolute JS ID; no generated JavaScript file is written to disk.

The default runtime entry imports that module. The `/manual` entry accepts the same shape without any virtual import, as shown in [its README](../packages/satchel/README.md#manual-mode).

## Vue usage and layout preservation

```ts
import { resolveSatchel } from '@dgtlss/satchel';

createInertiaApp({
  resolve: resolveSatchel(existingAppResolver),
  // Keep your Vue setup/mount callback.
});
```

`namespace::Page` remains unchanged in Inertia's response. The resolver checks **all override extensions first**, then all package extensions, and unwraps the winning module's `default` export. It returns the same component object, preserving a page's `defineOptions({ layout: BillingLayout })` property. Non-namespaced names and additional resolver arguments go to the original app resolver. Normal Inertia props and persistent layout behavior remain the adapter's responsibility; Satchel imports no private Inertia modules.

See [the Laravel example](../examples/laravel/README.md). Its fixture is loaded through a real Composer symlink and supports vendor and overridden Vue routes, PHP props, a persistent layout counter, and ordinary app pages.

## Generated page names

By default the plugin writes `resources/js/satchel-pages.d.ts`:

```ts
// Generated by vite-plugin-satchel. Do not edit.
export type SatchelPage =
  | "acme-billing::Invoices/Index"
  | "acme-billing::Invoices/Show";
```

Import the union with `import type { SatchelPage } from './satchel-pages'`. Names come from manifest registrations plus file inventory, including app-only pages under registered namespaces. They are sorted, deduplicated, and extensionless; empty inventory produces `never`. The union describes registered filenames, not the installed framework compiler's ability to render every extension. The example config registers only Vue, so `Dashboard.tsx` remains a PHP fixture and is excluded from this app's import map and union.

The output is generated and should be ignored by Git. Run Vite (or build) before consuming it in a clean checkout. Dev additions/removals and manifest changes regenerate it; unchanged output is not rewritten.

## Tailwind v4

Vendor files are usually excluded from automatic source detection. Add an explicit source relative to **the stylesheet**:

```css
@import "tailwindcss";
@source "../../vendor/acme/billing/resources/js";
```

That line is for a stylesheet at `resources/css/app.css`. Use one line per package, adjusting for its real installation path. The example uses `source(none)` and explicit app/vendor sources so the vendor class cannot pass accidentally through automatic workspace scanning. Vitest builds CSS with and without the vendor `@source`, including a Composer-style directory symlink; Playwright also checks the vendor page's generated padding/background in the production build. Class names still need to be complete static strings, following Tailwind's normal rules.

## Development and production behavior

Page content edits use Vue HMR and preserve the current document and layout state. Page additions/removals regenerate the import map/types and trigger a full reload. Manifest changes also reload, including PHP's atomic replacement; newly registered directories are watched and allowed. Dev errors are sent to Vite's overlay rather than silently retaining a stale map.

Production assets need rebuilding when page files, overrides, extensions, or registration change. Keep PHP and client builds on the same manifest/files, and update the application's Inertia asset version on deployment. The manifest remains machine-specific build input rather than a public asset.

## Checks and week 3 boundaries

```sh
npm ci
npm run build
npm test
npm run typecheck
composer install --working-dir=examples/laravel
npm run test:e2e
```

Vitest covers runtime resolution/errors, extension precedence, component identity, manual mode, manifest validation, declarations, symlink containment, real eager/lazy Vite builds, and Tailwind sources. One Playwright test exercises the built Laravel app, Vue navigation/props/layouts/overrides, template HMR without a reload, an atomic manifest reload, and adding/removing an override. PHP's existing suite remains a separate regression check. CI runs the JS/Vue checks on Node 24/PHP 8.3; Vite 7 is the declared plugin peer range.

There is no known resolver-level blocker for React or Svelte: the runtime is framework-neutral and preserves default export identity. Week 3 still needs each official Inertia adapter, its Vite/JSX or Svelte compiler plugin, peer dependencies, types, layout semantics, and browser/HMR coverage. They are **not** verified by the Vue example or the generic eager-function unit test.

SSR is also **unverified**. The plugin can generate eager maps, but that alone does not establish SSR support. Week 3 needs a server entry using the same plugin/manifest, Vue server rendering/hydration tests, framework dependency externalization checks, and matching deployment asset versions. For an installed npm runtime, expect to keep `@dgtlss/satchel` in `ssr.noExternal` so Vite transforms its virtual import rather than leaving `virtual:satchel/pages` for Node to load. Shared component layout defaults must not capture per-request state. No private Inertia imports should be needed.
